# Design: commitizen-based versioning and changelog

Date: 2026-10-06
Status: Approved (pending spec review)

## Problem

`generic-grader` releases are version bumps with no release notes. `make bump`
only edits `pyproject.toml`, commits, and tags; `make publish` pushes to PyPI
and pushes tags. There is no `CHANGELOG.md` and no GitHub Release step.

Two motivations, weighted equally:

1. **Downstream consumers** (the ENGR 13300 and EBEC content repos, which pin
   `generic-grader` versions) need to know what changed in order to decide when
   to upgrade.
2. **Release hygiene** — each PyPI release should carry documented notes as a
   matter of course.

## Goals

- Every release has a changelog entry, generated from commit history.
- The version bump and changelog update happen in one command.
- The workflow fits the existing `make bump` / `make publish` flow and the
  existing tag conventions.

## Non-goals (YAGNI)

- No GitHub Release automation. The changelog file is the source of truth;
  GitHub Releases are out of scope.
- No requirement to use `cz commit` interactively.
- No retroactive changelog for releases before 0.2.10.

## Decisions

| Decision | Choice | Rationale |
|---|---|---|
| Changelog form | Auto-generated from commits | Repo already has clean commit messages; avoids hand-maintenance drift |
| Generator | commitizen (`cz`) | Python tool, installs via `uv` as a dev dependency; `cz bump` replaces `make bump` |
| Commit convention | Conventional commits, going forward | Enables grouping into Added/Fixed/Changed sections |
| Enforcement | Local `commit-msg` hook **and** PR-title CI check | Rebase merges mean commit messages drive the changelog; the local hook enforces them, the CI check is a backstop |
| First entry | Hand-curate `0.2.10` | The 13 commits since `v0.2.9` are non-conventional, so cz would emit an empty section |

## Key constraint: rebase merges

Pull requests are rebase-merged, so every commit in a PR lands on `main`
individually. The changelog is therefore driven by the **commit messages**, not
the PR title. The local `commit-msg` hook is the primary enforcement point; a
CI check against the PR title is a backstop.

## Components

### `pyproject.toml`

Add `commitizen` to the `dev` optional-dependencies and add configuration:

```toml
[tool.commitizen]
version_provider = "uv"          # updates pyproject.toml AND uv.lock
tag_format = "v$version"         # matches existing v0.2.9 tags
annotated_tag = true             # matches existing annotated tags
major_version_zero = true        # 0.x: breaking changes bump MINOR, not MAJOR
changelog_incremental = true     # append, do not regenerate the whole file
changelog_start_rev = "v0.2.10"  # cz generates from 0.2.11 onward
bump_message = "bump: version $current_version → $new_version"   # conventional, passes the commit-msg hook
```

Do **not** set `name`. It is only needed by the `commitizen` version provider;
with `version_provider = "uv"` it makes cz try to locate an installed package
and fail with "The committer has not been found in the system." (verified
against commitizen 4.19.1).

Changelog generation is requested by the `Makefile` target (`cz bump
--changelog`) rather than by `update_changelog_on_bump = true`. Reason: the
0.2.10 section is hand-curated, and `update_changelog_on_bump` would make the
0.2.10 bump emit an empty auto-generated section that duplicates it. Keeping the
flag out of the config lets the one-time 0.2.10 bump run without changelog
generation while every later `make bump` still generates one.

Notes:

- `version_provider = "uv"` is `pep621` plus `uv.lock` maintenance. `uv.lock`
  records the project version (`version = "0.2.9"`, exactly once), so this
  removes the manual `uv sync` step from the current `make bump`.
- `major_version_zero = true` is required: the README states "expect breaking
  changes," and at `0.2.x` a `feat!:` must go `0.2.10 → 0.3.0`, not `1.0.0`.
- `bump_message` matches the existing `Bump version to 0.2.9` commit style.

### `CHANGELOG.md` (new)

Keep-a-Changelog-style, generated by cz. Seeded with a hand-curated `0.2.10`
section covering the real changes since `v0.2.9`:

- **Added** — `rtol`/`atol` threading through `array_diff_details` (#207);
  Python 3.14 support in CI.
- **Changed** — trusted library operations allowed during student imports
  (#200); library-origin security errors attributed to the grader rather than
  the student.
- **Fixed** — non-interactive matplotlib backend selected at runtime (#205);
  `Options.expected_distribution` given a per-instance default; deterministic
  unclosed-file message; test message checks that iterated over characters.

Dependency bumps and lint chores are omitted from the curated entry.

### `Makefile`

`bump` becomes a thin wrapper that also generates the changelog:

```makefile
bump:
	uv run cz bump --changelog
```

`publish` is unchanged (`build` + `uv publish` + `git push --follow-tags`).

The one-time 0.2.10 release is run directly as `uv run cz bump 0.2.10
--allow-no-commit` (no `--changelog`), because the 0.2.10 section is
hand-curated and the commits since `v0.2.9` are non-conventional (so cz cannot
detect an increment on its own).

### `.pre-commit-config.yaml`

Add the commitizen `commit-msg` hook so direct committers get local validation:

```yaml
  - repo: https://github.com/commitizen-tools/commitizen
    rev: v4.19.1
    hooks:
      - id: commitizen
```

Pin the hook `rev` to the same commitizen version installed as a dev
dependency (currently 4.19.1), mirroring the existing ruff hook practice.

### CI (`.github/workflows/`)

Add a job that validates the PR title with `cz check`:

```yaml
- run: uv run cz check --message "${{ github.event.pull_request.title }}"
```

### `README.md`

Add a short "Releasing" section documenting the workflow: write conventional
commit / PR titles, run `make bump`, review, run `make publish`.

## Data flow

```
conventional commits  ──►  rebase-merge to main
                                   │
                                   ▼
                          make bump  (uv run cz bump)
                                   │
              ┌────────────────────┼────────────────────┐
              ▼                    ▼                    ▼
      pyproject.toml          uv.lock            CHANGELOG.md
      (project.version)       (version)          (new section)
                                   │
                                   ▼
                        commit "Bump version to X" + annotated tag vX
                                   │
                                   ▼
                          make publish  ──►  PyPI + push tags
```

## Error handling / edge cases

- **No eligible commits:** `cz bump` exits with `NoneIncrementExit`. Document
  `--allow-no-commit` or an explicit `--increment` for forced releases.
- **Pre-commit auto-fix loop:** `cz bump` commits; if the pre-commit hook
  rewrites files it can fail the first commit. Use `cz bump --retry` (or
  pre-fix with ruff, per existing repo practice).
- **Version consistency:** `cz bump --check-consistency` verifies
  `pyproject.toml` and `uv.lock` agree before bumping.

## Testing / verification

- `uv run cz bump --dry-run` shows the detected increment and changelog diff
  without committing.
- `uv run cz check --message "feat: x"` passes; a non-conventional message
  fails.
- After the real bump: `git show --stat` confirms `pyproject.toml`, `uv.lock`,
  and `CHANGELOG.md` all changed; `git tag -l` shows the new annotated tag.
- `uv run pytest` still passes (no runtime code changes).

## Rollout

1. Add config + dev dependency; `uv sync`.
2. Add `CHANGELOG.md` with the curated `0.2.10` section.
3. Update `Makefile`, `.pre-commit-config.yaml`, CI, and README.
4. Run `uv run cz bump 0.2.10 --allow-no-commit` to produce `0.2.10` (version +
   tag; changelog already present).
5. Review, then `make publish`.
